# Architectural notes — `example_oemirot_dualslot_hwcrypto`

Working document. Part 1 describes **what the example actually is**, as built from the
sources in this folder. Part 2 is the **open discussion** on the architecture we want to
implement (signing scheme, flash layout, install mode, crypto backend).

> For a from-zero explanation of every configuration knob, the combinations that are
> legal, and a shortlist of complete candidate configurations, see
> [`ARCHITECTURE_CHOICES.md`](ARCHITECTURE_CHOICES.md).
> For the update sequence of each architecture, drawn step by step in flash,
> see [`UPDATE_FLOWS.md`](UPDATE_FLOWS.md).

Target: NUCLEO-C5A3ZG (STM32C5A3ZGT6, Cortex-M33 **without TrustZone in this setup**,
1 MB flash in 2 × 512 KB banks, 8 KB pages).
Sources referenced below are relative to `NUCLEO-C5A3ZG/`.

## 1. What this example is

### 1.1 Two-stage architecture

| Stage | Project | Role |
|---|---|---|
| Boot | `oemirot/` | OEM immutable Root of Trust: Secure Boot + Secure Firmware Update |
| Application | `appli/` | User firmware, carries the local update agent (YModem menu) |

OEMiRoT is **immutable**: it sits at flash offset 0, is write-protected (WRP) and is
hidden (HDP) before the jump to the application, so it cannot be read or altered by the
application. It is *not* field-updatable — that is the whole point of a RoT.

Boot chain:

```
Reset ──► BOOTADD = 0x08000000 (OB, BOOT_LOCK = locked)
        └► OEMiRoT  (0x00000 .. 0x11FFF)
             ├─ boot_platform_init()            apply dynamic prot. + verify static prot.
             ├─ MCUboot boot_go()               version/dependency/AR-counter, sig, decrypt+install
             ├─ boot_platform_quit()            update MPU for appli, close HDP, disable crypto clocks
             └─ jump via EXITHDPLIB (system-flash service, JumpHDPLvl2)
                  └► Application  (0x18400, header 0x400 skipped)
```

### 1.2 Flash map (`oemirot/flash_layout.h`)

| Offset | Size | Region |
|---|---|---|
| `0x00000` | `0x12000` (72 KB) | OEMiRoT code |
| `0x12000` | `0x2000` | Keys area (auth pubkey **hash** + raw enc private key) |
| `0x14000` | `0x2000` | Anti-rollback NV counters |
| `0x16000` | `0x2000` | Image hash references (fast-boot cache) |
| `0x18000` | `0x74000` (464 KB) | **Primary (active) app slot** — bank 1 |
| `0x8C000` | `0x74000` (464 KB) | **Secondary (download) app slot** — bank 2 |

Derived protections: `WRP 0x00000..0x13FFF` (code + keys), `HDP 0x00000..0x17FFF`
(code + keys + counters + hash refs — hidden after boot). Data-image slots exist in the
design (`FLASH_*_DATA_SLOT_*`, `MCUBOOT_DATA_IMAGE_NUMBER`) but are **sized to 0** here.

Notable: the layout is *symmetric* — both slots are the same size, which is what a swap
or mirror scheme would need. It is **not** bank-aligned, however: bank 1 ends at
`0x80000`, so the primary slot holds 416 KB in bank 1 and spills 48 KB
(`0x80000`–`0x8BFFF`) into bank 2. Only the secondary slot sits wholly inside one bank.
This matters twice: for read-while-write (application code lives in both banks) and for
any future bank-swap scheme, which would need each image contained in its own bank.

`region_defs.h` turns these offsets into addresses/MPU regions; `appli/appli_flash_layout.h`
is **generated by the appli prebuild** from the RoT headers, so the application never
redefines the map — it inherits it.

### 1.3 Install mode: dual-slot **overwrite**

- `MCUBOOT_OVERWRITE_ONLY` is set; `MCUBOOT_SWAP_USING_MOVE` is present but commented out.
- New image is downloaded by the application over YModem into the **secondary slot**.
- The application then writes a **magic trailer** at the end of the secondary slot
  (`FLASH_SECONDARY_APP_INSTALL_REQ_OFFSET`, see `appli/fw_update_app.c`) and resets.
- At next boot OEMiRoT validates the candidate and **copies it over the primary slot**.
  The previous image is destroyed — **no automatic rollback to the old firmware**.
- `MCUBOOT_VALIDATE_PRIMARY_SLOT` re-verifies the primary slot after installation and on
  every boot; `MCUBOOT_ROM_FIXED` binds the image to its primary-slot address (no
  position independence, so it can only run from the primary slot).

Consequence: an image that is signed correctly but *bricks* at runtime cannot be reverted
by the bootloader. Recovery = a new download, i.e. the app must still be able to run its
update agent, or the board must be reprogrammed.

### 1.4 Crypto & trust anchors

Image format is MCUboot: `header (0x400) | payload | TLVs (signature, hashes, dependencies)`.

| Property | Value here |
|---|---|
| Signature | **ECDSA P-256 / SHA-256** (`MCUBOOT_SIGN_EC256`) |
| Encryption | **ECIES-P256 + AES-128-CTR** (`MCUBOOT_ENCRYPT_EC256`, `--encrypt-keylen 128`) |
| Auth trust anchor | **SHA-256 hash of the public key** in flash (`MCUBOOT_HW_KEY`), full pubkey travels in the image TLV |
| Decryption key | **raw EC private key** in flash (`MCUBOOT_RAW_ENC_KEY`) |
| Anti-rollback | `MCUBOOT_HW_ROLLBACK_PROT` + NV counters in flash (`boot_nv_counters.c`, CRC-protected, wear-levelled by append) |
| FI hardening | `MCUBOOT_FIH_PROFILE_HIGH`, double signature verification, `fih_delay` |

Keys are provisioned into `FLASH_KEYS_OFFSET` from
`provisioning/keys/oemirot_authentication.pem` (public, hashed) and
`oemirot_encryption.pem` (private, raw) via `provisioning/xml/oemirot/oemirot_keys_config.xml`
and STM32TrustedPackageCreator. `oemirot/keys_map.c` is the only code that knows where they live.

**Hash-reference fast boot** (`MCUBOOT_USE_HASH_REF`, `boot_hal_hash_ref.c`): after a
successful full verification the SHA-256 of the image is cached in the hash-ref page; on
subsequent boots a hash match lets OEMiRoT *skip the ECDSA verification*. This is the main
boot-time optimisation — it trades one signature check per boot for one flash page and the
assumption that the hash-ref page is HDP/WRP-protected.

### 1.5 What "hwcrypto" changes

This example differs from the sibling `oemirot_dualslot` in exactly one architectural axis
— the **crypto backend**. Diff of the two trees:

| | `oemirot_dualslot` (sw) | `oemirot_dualslot_hwcrypto` |
|---|---|---|
| mbedTLS ALT | `MBEDTLS_STCRYPTOLIB_{AES,ECDSA,ECDH}_ALT` | `MBEDTLS_HAL_{AES,ECDSA,ECDH,ECP}_ALT` |
| Backing HW | software (STCryptoLib) | **PKA** (ECDSA/ECDH), **SAES** (AES), **HASH** (SHA-256), RNG |
| Extra drivers | — | `mx_pka.c`, `mx_saes.c` (+ `mx_hash.c`, `mx_rng.c` in both) |
| mbedTLS heap | `0x1000` | `0x800` (HW offload ⇒ less scratch RAM) |
| App slot size | `0x14000` (80 KB) | `0x74000` (464 KB) |

So the hwcrypto variant is: **same boot architecture, crypto offloaded to PKA/SAES/HASH,
half the mbedTLS heap, and a full-bank slot layout.** The RoT code itself
(`boot_hal.c`, `low_level_security.c`, `flash_layout.h` structure) is otherwise identical.

Crypto clocks are enabled in `boot_platform_init()` and explicitly **disabled** in
`boot_platform_quit()` before the jump — the application does not inherit an armed SAES/PKA.

### 1.6 Runtime protections

Applied by `low_level_security.c`:

- **Static (checked, not set)** — `SECURITY_CheckStaticProtections()` verifies option bytes
  and halts if any is wrong: BOOTADD, BOOT_LOCK, WRP on RoT code+keys, HDP area bounds,
  SRAM2 ECC, SRAM2 erase-on-reset, RDP level ≥ `OEMIROT_OB_RDP_LEVEL_MIN` (RDP 0 in this
  dev configuration; provisioning can raise it).
- **Dynamic (set)** — MPU (7 regions during RoT: code XO-RO, slots RW-NX, SRAM RW-NX,
  peripherals, EXITHDPLIB thunk, boot-data, system mem), tamper (internal tamper 9,
  confirmed mode, secrets erased on fault), SRAM/flash ECC, ICache.
- **Flow control** (`OEMIROT_FLOW_CONTROL`, `boot_hal_flowcontrol.h`) — every protection
  step increments a redundant counter; `FLOW_CONTROL_CHECK()` at stages 1..4 catches a
  skipped step (fault injection). Each protection is applied and checked **twice**.
- On jump: MPU reduced to a single RO/X region on the app, HDP closed by the system-flash
  `JumpHDPLvl2` service so the RoT code/keys become unreadable, MSPLIM cleared, RAM wiped
  (`boot_clear_ram_area()`).

### 1.7 Build & provisioning tooling

- `provisioning/provisioning.py` → drives the shared framework in
  `utilities/rot_provisioning/` (git submodule, **not populated in this checkout**),
  configured by `provisioning/config/example.json` (board, memory geometry, option-byte
  pre/post-flash sequences, `install_mode: overwrite`, `isolation: false`, `lifecycle: rdp`).
- `oemirot/project_oemirot.py` (prebuild) and `appli/project_appli.py` (pre/postbuild)
  keep `flash_layout.h`, the linker scripts (`.icf`/`.sct`/`.ld`) and
  `appli_flash_layout.h` in sync, and drive image signing/encryption from the XMLs in
  `appli/xml/` and `provisioning/xml/`.
- Toolchains: EWARM project provided; Open-CMSIS (`open-cmsis/*.csolution.yml`) present.
  README states **only EWARM is supported** today.
- Security classification: **Medium** (`SW_Security_Level.md`).

### 1.8 Architectural takeaways

1. **Single trust anchor pair** (one auth key hash, one enc private key) for all images —
   no per-image or per-vendor key separation.
2. **Immutable RoT, no RoT update path.** Any bug in OEMiRoT is permanent in the field.
3. **No rollback capability** (overwrite mode), but **strong anti-rollback** (NV counters).
4. **Flash cost is the dominant constraint**: 2 × 464 KB slots + 72 KB RoT + 24 KB metadata
   ≈ the whole 1 MB. Usable application size is ~45 % of flash.
5. **No TrustZone / no isolation** in this configuration; separation relies on MPU + HDP +
   the one-way jump.
6. **No room reserved for device data.** The two slots run to the top of flash
   (`0x100000`), so there is no region for calibration or configuration written by the
   device itself. Adding one means shrinking both slots — see
   [`ARCHITECTURE_CHOICES.md`](ARCHITECTURE_CHOICES.md) §2.13.

## 2. Open architecture discussion

Decisions to make, with the trade-offs as they apply to an STM32C5-class part.

### 2.1 Flash layout / install mode

| Option | Flash cost | Rollback on bad image | Install time | Notes |
|---|---|---|---|---|
| **Single slot** (secure boot only) | 1 × app | none | none | No in-field update, or update via a separate loader. Max app size. |
| **Dual slot overwrite** *(this example)* | 2 × app | **no** | copy whole image | Simplest, deterministic, power-fail safe if the copy restarts. |
| **Dual slot swap (`SWAP_USING_MOVE`)** | 2 × app + 1 sector scratch | **yes** (auto-revert if app doesn't confirm) | ~2× copy | Needs `MCUBOOT_SWAP_USING_MOVE` (already stubbed in `mcuboot_config.h`), trailer + spare-sector space, and a confirm step in the app (already written, compiled out). The image still runs from the primary slot, so it keeps its current link address. |
| **Mirror / bank swap (`SWAP_BANK` OB)** | 2 × app (one per bank) | **yes**, instantaneous | ~0 (option-byte swap) | Exploits the C5's dual-bank + `SWAP_BANK` OB. Needs a re-layout first: today the primary slot straddles the bank boundary. Both images must be linked at the *same* logical address. Requires an OB write in the RoT and a reset. |

Questions to settle:

1. **Do we need field rollback**, or is "download again" acceptable? This is the single
   decision that picks overwrite vs. swap/mirror.
2. **Is the ~464 KB app budget enough?** If not, the dual-slot assumption itself is on the
   table: external flash for the download slot (QSPI/OSPI part driver, `w25q128j` exists in
   `part_drivers/`) would free ~464 KB of internal flash and let the primary slot grow.
3. **Do we want a separate data image** (`MCUBOOT_DATA_IMAGE_NUMBER = 1`)? The plumbing is
   already there and currently sized to 0. Useful for config/certificates updated
   independently of code; costs two more slots.
4. **Do we want the update agent in the application, or a dedicated loader?** Today the app
   owns YModem. If the app is bricked, so is the update path. A small third stage (or
   keeping ST's Open Bootloader / a DFU path) decouples them.

### 2.2 Signing / authentication method

| Scheme | Verify cost on C5 | Key/anchor size | Comment |
|---|---|---|---|
| **ECDSA P-256 + SHA-256** *(this example)* | fast with **PKA** | 32 B pubkey hash | Default, well supported, HW-accelerated. |
| ECDSA P-384 | ~2–3× slower | 48 B | Only if a stronger classical level is mandated. |
| RSA-2048/3072 PSS | slower verify, big TLVs | larger | Larger images, larger boot time; no reason unless PKI is fixed. |
| **Ed25519** | no PKA path | 32 B | Attractive on paper, but loses hardware acceleration here. |
| **HMAC / symmetric (AES-CMAC)** | fastest | shared secret on device | Only viable if the signing secret never leaves a HSM *and* device compromise is acceptable — generally rejected for secure boot. |
| PQC / hybrid (LMS, ML-DSA) | large signatures, slow | large | Worth raising only if a long-lived product must survive a CNSA 2.0-style mandate. |

Related sub-decisions:

- **Trust anchor form**: pubkey **hash** in flash (`MCUBOOT_HW_KEY`, current) vs. full pubkey
  embedded in RoT code. Hash is smaller and lets the key be provisioned per-device/per-batch
  without rebuilding the RoT — keep it.
- **Key count / rotation**: one key for everything today. Do we want (a) separate keys for
  app vs. data images, (b) a key-revocation slot (a second anchor, promoted via NV counter)?
  Since the RoT is immutable, **key rotation must be designed in now or it does not exist.**
- **Signature policy**: single vs. double verification (double is on, costs time, buys FI
  resistance).
- **Hash-reference fast boot**: keep? It removes the per-boot ECDSA cost but makes the
  hash-ref page security-critical. Decide explicitly per boot-time budget.

### 2.3 Confidentiality of the image

Currently **ECIES-P256 + AES-128-CTR**, with the ECIES private key stored raw in flash
(readable by anyone who defeats RDP/HDP). Alternatives worth discussing:

- **AES-256** instead of 128 (`--encrypt-keylen 256`) — near-free with SAES.
- **SAES hardware key / DHUK-wrapped key** instead of a raw key in flash: the decryption key
  never exists in readable form. This is the main hardening step available on this silicon
  and the natural next move for the "hwcrypto" variant.
- **No encryption at all** — if the firmware is not confidential, dropping it removes the
  raw private key from flash entirely and simplifies the provisioning chain.

### 2.4 Crypto backend

`hwcrypto` (PKA/SAES/HASH) vs. software (STCryptoLib): HW wins on boot time and RAM
(`0x800` vs `0x1000` mbedTLS heap) and is what the C5 is for. The software variant is only
interesting for portability to parts without PKA/SAES. **Recommendation: stay on hwcrypto**,
and evaluate SAES-key-in-hardware (§2.3) on top of it.

### 2.5 Isolation model

Currently `isolation: false`, no TrustZone: MPU + HDP + one-way jump. Open questions:
does the product need a secure/non-secure split (TF-M style), a runtime secure service
(e.g. keys usable by the app without exposing them), or is boot-time-only protection enough?
This choice interacts with the flash layout (isolation adds secure/non-secure slot pairs).

### 2.6 Lifecycle / production

`example.json` targets `lifecycle: rdp`, `min_rdp_level = RDP_0`, `final_rdp_level = RDP_0`
— a **development** posture. For production: RDP level 1/2 (or 2-WBS for returns),
debug-authentication policy, provisioning of per-device keys, and whether regression
(`regression_rdp_key.txt`) stays possible at all. Worth deciding early, since the
option-byte sequences in `example.json` encode it.

### 2.7 Suggested decision order

1. Rollback requirement → install mode (overwrite / swap / mirror).
2. App size budget → internal vs. external secondary slot; data image yes/no.
3. Signature scheme + **key rotation/revocation** strategy (irreversible once RoT is locked).
4. Encryption: keep / drop / move key into SAES hardware.
5. Isolation model.
6. Lifecycle & RDP policy for production.

Items 3 and 6 are the ones that cannot be changed after the RoT is provisioned and locked —
they should be settled first even though they are listed after the sizing questions.
